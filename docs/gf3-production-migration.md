# GOLD FIRST 3シート統合の本番移行手順案

本番作業は別途承認後に実施する。検証用GAS、トークン、固定の車両・受付・ドライバーIDは本番へコピーしない。

## 実績処理の移行コード

`node scripts/gf3-build-canonical-actual.mjs build/gf3-canonical` で実績処理の共通モジュールを生成する。入口は `GF3_RunCanonicalVehicleReceipt_`。認証済みの既存GAS入口から、認可済み台帳、受付ID・VehicleID・DriverID、既存履歴の読取・追加・状態遷移を担うアダプター、書込許可確認を渡す。取消時も受付履歴に記録した組合せを渡す。履歴側の状態遷移では現在状態と最新実績を照合する。

共通モジュールは車両台帳・名変待ち管理・ドライバーマスターだけを参照する。検証側は専用GAS、固定の試験レコード、検証Supabaseの境界を維持する。本番の既存入口をこのモジュールに切り替える作業は、実稼働版の棚卸しと検証が済んでから行う。

## 写真・Driveの既存入口向け差し替え候補

`node scripts/gf3-build-legacy-media-cutover.mjs SOURCE OUTPUT` で、確認した50・70・80番のソースからDrive準備、写真保存・取消の差し替え候補を生成する。共通実績モジュールと組み合わせて使う。車両台帳に写真親フォルダと車両書類フォルダの列があること、既存リンクが同じDriveフォルダを指すことを先に照合する。生成処理は対象ソースが一致しない場合、または差し替え対象に旧シートの取得が残る場合に停止する。候補は検証GASの専用写真経路と別のため、専用検証GASへ重ねて追加しない。

## 車両同期・画面リンク・予定処理の差し替え候補

車両同期・画面リンク・予定処理の差し替え候補は `node scripts/gf3-build-legacy-sync-cutover.mjs SOURCE OUTPUT` で生成する。共通実績コードと写真・Drive差し替え候補と組み合わせる。予定管理の予定IDと既存イベントIDを保持し、イベントを解決できない場合は更新を停止する。候補の生成に使ったローカルソースと実稼働版の一致確認、初期化・表示設定・既存外部APIの依存解消が済んでから切り替える。

## LINEマイページの検証設定

検証用LIFFの登録済みURLからレビュー版マイページを開く。検証Edge Functionの `GF3_MYPAGE_LINE_CHANNEL_ID` には同じLIFFのチャネルIDを設定する。検証用LINEアカウントと既存DriverIDの一意の紐付けを確認し、別ドライバーで閲覧できないことを照合する。本番LINEチャネルの設定は変更しない。

## 移行前

1. 本番GASの配備版・トリガー一覧・運用中のAPI版、台帳と旧2シートの値・数式・入力規則、予定IDとCalendarEventID、Drive書類リンクの現状を控える。旧シートは保管する。
2. 車両台帳のVehicleID、ドライバーマスターのDriverID、名変待ち受付と割当VehicleIDの重複・欠損を照合する。LINEマイページは既存認証と契約経路を使い、受付と車両を明示的に照合する。
3. 検証用LINEユーザーと既存イベントID付きの検証用カレンダーで、マイページの本人表示とイベント更新を確認する。車検・点検・納車・返却の既存IDを更新前後で比較する。旧シートを参照する既存GAS入口とトリガーの棚卸しを終える。
4. 月別納車管理のA:C、E:I、K:Oを既存の結果と照合する。取消済みを除く同月の納車実績・明細・集計の一致を確認する。返却後の再割当、書類リンクの復元、直接編集後の同期も確認する。

## 切替と復旧

1. 切替時点のスナップショットとロールバック先を確定する。旧・新の同期トリガーが同じ対象を書かないよう、切替対象を運用単位で明示し、旧同期を停止してから新同期を開始する。
2. 読み取りと同期の照合後、承認された範囲で書き込みを有効化する。実績受付IDで台帳と履歴を突合し、Driveリンク・LINE・既存CalendarEventIDを確認する。
3. 差分が解消しない場合は新規実績書き込みと新同期を停止し、配備を控えた版へ戻す。未完了受付と切替後の正当な編集を照合し、該当行のみ復旧する。既存イベントの再作成、台帳全体の上書き、旧シートの削除は行わない。
