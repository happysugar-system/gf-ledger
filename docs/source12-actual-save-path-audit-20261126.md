# 実際の本体GAS (12) を参照した接続監査（2026-11-26）

出典: 利用者提供の本体GAS JSON「【開発版】GOLD FIRST 整理 (12).json」（全59ファイル）。秘密情報・原文全量はリポジトリへアップロードしていない。Workに原本を添付してレビューすること。フォームJSONとは異なるGASプロジェクト。

## 実際の変更ポイントと既存挙動

- `25_車両実績.gs`：`GF_実績受付本体_25` で受付ID重複と対象日、貸出/返却の状態を検証。`GF_実績キューワーカー` は、実績履歴作成→`行を書き込む_(v.sheet,v.row,update)`→`車両台帳の1台を同期する(v.row,true)`→実績履歴の変更後を確定→完了、の順序。返却時の `update` は現在使用者・DriverIDを空欄にする。
- `24_実績取消.gs`：`GF_実績履歴を保存_26` は変更前・変更後JSONを保持。`GF_実績取消を実行する_26` は新しい完了実績の有無と日付、一部の変更後の値を比較して台帳へ復元し、その後キュー同期。**現状の履歴対象に前使用者／前々使用者／前DriverID／前々DriverID／過去書類がない**。将来の取消で上書き防止のため、履歴記録と復元対象の拡張が必要。
- `30_車両同期.gs`：`車両台帳の1台を同期する` は `現在使用者変更=true` のとき、旧 `利用者管理` から前使用者名を取り出し台帳 `前使用者` を更新する。さらに `利用者管理を更新する_` は、旧使用者名・DriverID・書類を `利用者管理` の前使用者欄へ保持。**台帳正本化後にこのロジックを残すと二重履歴・旧シート依存を発生させる**。
- `名変割当同期.gs`：`GFW_割当本体_` は空車・現在使用者/DriverID空欄を検査し、3シートを edits 配列で保存、失敗時 snapshot 復元。`GFW_取消本体_` は使用者・DriverID一致を確認し、3シートに復元。履歴移動の対象判定は本実装と一体化が必要。別プロジェクトのフォーム側に同名関数があるため重複定義禁止。
- `60_書類PDF.gs`：`車両書類を保存する_` はDriveに登録ごとの新しいフォルダとPDFを作り、`利用者管理` M列／`車両状況` R列へPDF URLを書き、その後 `GF_車両書類を同期する_28` で台帳を更新。**既存のDrive登録フォルダは削除・再利用しない**。旧2シート書込解消時は、PDFの保存と取消情報を保ちつつ台帳BJへ統一。

## 接続の安全条件

1. 利用者変更の確定境界を決める。名変割当だけで世代移動しない場合、返却確定時に現在→前、前→前々（氏名・ID・書類一組）を同一履歴記録と台帳更新で行う。貸出開始／代車は重複移動しない。
2. 現在書類リンクの取得には `getRichTextValues/getFormulas/getValues` 等のリンク情報が必要。表示文字だけをスナップショットに保存してから `setValue` で戻すとクリック可能URLを失うため、URLと書式を検証して扱う。
3. `GF_実績履歴を保存_26` が記録した「変更前」、`GF_実績履歴の変更後を確定_26` が記録した「変更後」と実際の台帳を全対象フィールドで比較し、変更後不一致なら取消を中止。二重取消は既存の取消済判定を維持。
4. 書類PDFの登録・取消、同じ車両に並行するGASプロジェクトの書込、マイページ同期、CalendarEventIDを巻き込むため、純関数の単体合格だけで本番接続完了とはしない。
5. 本番のスクリプトプロパティ・トリガー・現行配備版とA～BKの入力規則を変更しない。追加列の承認は別。旧2シートは削除せず移行・検証後に依存を停止する。

## 3世代履歴の保存候補と確認結果

`GF_OperationalHistoryPlan_` は氏名・DriverID・書類URLを組にして、同一車両の割当→貸出→返却→取消を計算する。割当・貸出で世代は進めず、返却確定時に現在から前、前から前々に退避する方式を検証候補とした。返却取消は9項目の現在値が同じ受付の変更後と一致する場合だけ復元する。変更前と一致する再取消は何もしない。旧データの氏名とIDが片方しかない場合や、書類ラベルからURLを確定できない場合は自動更新の対象にしない。

添付59ファイルの現物を確認した。本体の旧名変割当は「貸出中」への変更とDriverID発番を含むため、そのまま再利用すると今回の合意に反する。組み込み先は照合済みの動的割当経路とする。本体の25番の返却、24番の取消、30番の旧使用者転記は同時に対応が必要。24番は台帳書込前に貸出先の副作用を起こす経路があるため、復元可否の検査はその前に置く。PDF保存・取消が更新する書類リンクも比較の対象にする。

既存35件と追加2件を実行した。追加は操作を連続させた9項目の比較、取消再送、途中変更の拒否、別利用者・不明履歴の拒否を確認する。GASの実書込経路への適用、リッチテキストの書込と再読取、既存検証ブックでの操作は未実施。候補は書込みや公開RPCを持たないため、単独でApps Scriptに貼っても操作は切り替わらない。

本体の実地検証時は既存の検証プロジェクト・ブックを照合し、本番固定参照（台帳・Drive・カレンダー・LINE等）を検証値に限定できる経路を使う。失敗時は新経路を止め、現行配備版に戻し、取消・返却ログと台帳の使用者・書類リンクを照合して個別復旧する。

## 検証用の本体差し替えファイルを生成

リポジトリ直下で `python scripts/gf-patch-source12-return-history.py BACKUP.json OUTPUT_DIR` を実行する。入力は添付の本体(12)、出力は未作成フォルダを指定する。既知の接続箇所が各1か所である場合にだけ、24・25・30番と履歴の追加3ファイルを出力する。バックアップ原本はGitHubに保存しない。生成した6ファイルの構文を確認し、履歴関連の自動テスト38件が合格した。

- 25番では返却時に計画を既存の受付ID履歴に先に記録し、通常の台帳変更と履歴差分を1回のSheets APIバッチで書く。中断再開では実績日と記録済み履歴の変更後9項目を照合する。
- 24番では取消前に変更後9項目と現在値を比較し、履歴と台帳の復元をまとめて書く。進捗・台帳の競合は実環境で別途試験する。
- 30番では履歴が確定した返却、または検証フラグが有効な取消キュー同期で、旧利用者管理から前使用者を再転記しない。BJの現行車両PDFは車両単位の共有リンクとして保持し、返却時に同じURLを前使用者の書類へ退避する。動的割当、60番のPDF処理と既存のカレンダー・Supabase呼出しは変更していない。

反映先は既存検証GASのうち、実績処理25・24・30を収録し、既存検証ブックと検証専用Drive・カレンダー・LINE・Supabaseだけを参照することを確認できたプロジェクトに限定する。ブックIDの一致だけでは本体の副作用を隔離できない。対象の配備先と接続先を確認後、現行版を控え、24・25・30番を差し替え、生成された残り3ファイルを同名重複なしで追加する。既存プロパティに `GF_TEST_RETURN_HISTORY_ENABLED=true` のみ追加し、履歴9列の一意性とSheetsの高度なサービスを確認する。台帳やDriveへの書込を伴う実地試験は、この条件を満たす既存プロジェクトが確認できるまで行わない。

実地試験には未使用の検証受付と車両を使う。割当→貸出→返却→取消では貸出状態が戻るので、再割当前に再返却する。各操作後に台帳・履歴と書類のリンクを読み直し、返却バッチの前後で停止した場合、同期失敗・再試行、CalendarEventID、Supabaseの複製も照合する。本番移行は別承認。検証から戻す場合は新規操作を止め、処理途中・取消途中の受付を台帳と照合し、フラグと配備版を元に戻す。
