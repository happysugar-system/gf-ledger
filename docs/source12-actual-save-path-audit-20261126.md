# 実際の本体GAS (12) を参照した接続監査（2026-11-26）

出典: 利用者提供の本体GAS JSON「【開発版】GOLD FIRST 整理 (12).json」（全59ファイル）。秘密情報・原文全量はリポジトリへアップロードしていない。Workに原本を添付してレビューすること。フォームJSONとは異なるGASプロジェクト。

## 実際の変更ポイントと既存挙動

- `25_車両実績.gs`：`GF_実績受付本体_25` で受付ID重複と対象日、貸出/返却の状態を検証。`GF_実績キューワーカー` は、実績履歴作成→`行を書き込む_(v.sheet,v.row,update)`→`車両台帳の1台を同期する(v.row,true)`→実績履歴の変更後を確定→完了、の順序。返却時の `update` は現在使用者・DriverIDを空欄にする。
- `24_実績取消.gs`：`GF_実績履歴を保存_26` は変更前・変更後JSONを保持。`GF_実績取消を実行する_26` は新しい完了実績の有無と日付、一部の変更後の値を比較して台帳へ復元し、その後キュー同期。**現状の履歴対象に前使用者／前々使用者／前DriverID／前々DriverID／過去書類がない**。将来の取消で上書き防止のため、履歴記録と復元対象の拡張が必要。
- `30_車両同期.gs`：`車両台帳の1台を同期する` は `現在使用者変更=true` のとき、旧 `利用者管理` から前使用者名を取り出し台帳 `前使用者` を更新する。さらに `利用者管理を更新する_` は、旧使用者名・DriverID・書類を `利用者管理` の前使用者欄へ保持。**台帳正本化後にこのロジックを残すと二重履歴・旧シート依存を発生させる**。
- `名変割当同期.gs`：`GFW_割当本体_` は空車・現在使用者/DriverID空欄を検査し、3シートを edits 配列で保存、失敗時 snapshot 復元。`GFW_取消本体_` は使用者・DriverID一致を確認し、3シートに復元。履歴移動の対象判定は本実装と一体化が必要。別プロジェクトのフォーム側に同名関数があるため重複定義禁止。
- `60_書類PDF.gs`：`車両書類を保存する_` はDriveに登録ごとの新しいフォルダとPDFを作り、`利用者管理` M列／`車両状況` R列へPDF URLを書き、その後 `GF_車両書類を同期する_28` で台帳を更新。**既存のDrive登録フォルダは削除・再利用しない**。旧2シート書込解消時は、PDFの保存と取消情報を保ちつつ台帳BJへ統一。

## 接続の安全条件

1. 利用者変更の確定境界を決める。名変割当だけで世代移動しない場合、返却確定時に現在→前、前→前々（氏名・ID・書類一組）を同一履歴記録と台帳更新で行う。貸出開始／代車は重複移動しない。
2. 現在書類リンクの取得には `getRichTextValues/getFormulas/getValues` 等のリンク情報が必要。表示文字だけをスナップショットに保存してから `setValue` で戻すとクリック可能URLを失うため、URLと書式を検証して扱う。
3. `GF_実績履歴を保存_26` が記録した「変更前」、`GF_実績履歴の変更後を確定_26` が記録した「変更後」と実際の台帳を全対象フィールドで比較し、変更後不一致なら取消を中止。二重取消は既存の取消済判定を維持。
4. 書類PDFの登録・取消、同じ車両に並行するGASプロジェクトの書込、マイページ同期、CalendarEventIDを巻き込むため、純関数の単体合格だけで本番接続完了とはしない。
5. 本番のスクリプトプロパティ・トリガー・現行配備版とA～BKの入力規則を変更しない。追加列の承認は別。旧2シートは削除せず移行・検証後に依存を停止する。
