# GF138後続同期の実地検証と移行

## 実地検証

検証用の車両台帳とLINE受付ブックに、TEST-R02の受付、LINE行、登録済みを模したGF138履歴、検証専用ドライバー、未割当の名変待ち行を用意した。既存のTEST-R01を変更しない。名変待ち行のDriverID空欄は、後続同期で書き込むために残してある。

コミット 6d36639 の 172_GF138_名変待ち連携.gs が入っている検証GASにだけ、test/GFA_TEST_R02.gs を追加する。既存の GFA_APPROVED_BOOK_ID、GFA_APPROVED_LINE_BOOK_ID が検証専用の2冊を指し、GFA_WAITING_LINK_ENABLED が true であることを確認する。GFA_TEST_R02_実地確認 を1回実行する。診断、初回、再実行、同一受付の登録再試行を順に実行し、DriverID以外が変わっていないことを確認する。合格条件は初回 updated:1、再実行 updated:0、再登録 already_registered。未割当のTEST-R02以外を初回条件のために書き換えない。

この試験はGF138が作成する履歴を模したもの。GF138・GF143の実処理を試験する際は別の新規ダミー受付を使い、LINE受付と車両台帳の各接続先、GF138の書き込みフラグ、GF143のモード・必須列、Drive等の参照先を隔離したことを先に確認する。保存済みの本番GF138は本番向け固定IDを持つため、GFAの2つのプロパティだけでは一連の処理の接続先は切り替わらない。空欄からの補完試験と、上流が実際に履歴・DriverIDを生成する試験の結果はそれぞれ記録する。

認可確認では、既存スタッフ用サーバー入口を特定したうえでログインなし・権限なしを拒否し、正しい権限での登録と再登録を確認する。内部関数の末尾の下線と書き込みフラグは、スタッフ権限そのもののチェックとは別に扱う。

## 承認後の移行

1. GASソース、デプロイ版、既存トリガー、名変待ち管理の書式・データを控える。既存GFA関数と同名定義を照合し、統合版172を1組にする。
2. 承認された本番の接続先を既存プロパティで照合する。連携を無効にした状態で配置し、列追加診断を実行する。N:Pの空きと既存列を確認してから LINE受付ID・受付識別子・DriverID の3見出しだけを追加する。
3. 読取診断と認可済み入口を確認してから有効化する。既存GF138トリガーを使い、同じトリガーを追加しない。最初の受付でGF138・GF143・GFAのログと名変待ちの3項目、再実行時の重複防止を確認する。
4. 異常時はGFA_WAITING_LINK_ENABLEDを無効化して後続の書込を止める。必要に応じて保存前のソースを復元し、Webアプリの配信版も戻す。切替時の記録と比較して影響行だけを復旧する。3列に保存済みの紐付けを一括削除しない。
