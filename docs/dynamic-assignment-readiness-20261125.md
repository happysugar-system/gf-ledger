# 動的な車両割当の本番移行判定

今回の作業は 7567297 を親とする検証ブランチ。既存の 11/24 進捗検証ブランチは履歴が分岐しているため、双方の変更を本番に適用する場合は稼働ソースで統合する。

## 保存と既存同期

- GF_ReceiptAssignmentPlan.gs の照合を使用する。LINE受付ID・既存DriverID・VehicleIDが一致する一組に限る。区分/ステータスは更新項目に含まれない。かつてと同じDriverIDが別車両にある場合は確認待ち。業務上の複数台同時割当は新たに有効化していない。
- GF_ReceiptAssignmentSave.gs はロック下で対象3シートを更新する。Sheets APIでまとめて書き、応答消失時は再読取する。同じ状態では再書込しない。台帳を別のプロジェクトや画面から同時編集する場合、ScriptLockが双方に効くとは限らない。実地試験で確認する。
- GF_ReceiptAssignmentReplica.gs は既存GF_SBの1台読取診断を用いて車両JSONと台帳を照合する。同期遅延・障害・重要キー欠落・値不一致は reconciliation_required。既存定期同期が完了したら同じ操作の再確認で verified を返す。名変待ちとドライバーマスターの整合性は台帳側で確認する。
- 保存済みソースでは GF154 が 車両台帳の1台を同期する(row,true) を呼ぶ。同期関数の現行本体・副作用が確定しておらず使用しない。GF_SB_統合同期 は車両・ドライバー・受付をまとめて処理する。GF_SB_1台だけ手動同期 は自動実行禁止で初期状態では安全停止する。各書込処理を割当保存から追加起動しない。
- goldfirst-demo の割当複製は record JSON、確認済み本番候補の単体読取は gf_vehicles の vehicle_data。両者の形状が異なる。テスト環境で本番副作用を生まないため、本番用診断関数をそのままデモへ向けない。

## 後続の接続と試験

1. 稼働するスタッフ書込APIとGASのエントリーポイント、トリガーと実行主体を特定する。既存スタッフ認証を通したサーバーで受付・DriverID・VehicleIDを解決し、署名検証後に内部関数を呼ぶ。操作IDと受付の版を照合し、古い画面で取消・再割当を取り違えないようにする。未認可と動的な対象一覧の実機確認が必要。
2. テスト専用の新規車両と受付で割当、取消、再割当の幹を操作する。3シート、実行ログ、同期先の対象1台を同じIDで突合する。受付と車両を取り違えたリクエスト、二重押下、応答消失時も確認する。
3. 進捗・納車可能日と確定日を登録した後の取消を止め、台帳直編集からの同期、本人のみのマイページ表示まで確認する。今回の変更は既存の進捗・マイページ・カレンダー・認証のコードに触れていない。

2026-11-25の読取確認で TEST-R04 は名変待ちに1件・D999904・未割当。検証Supabaseには既存の割当複製・進捗が各1件。今回の動的割当で実データは書き換えていない。自動試験は第3シート更新後の結果、二重保存、同時実行のロック、再割当、進捗後の取消、応答消失や複製不一致を模擬確認した。

## 承認後の切替と復旧

本番移行は実地合格と承認まで保留。切替前にGASとスタッフAPIの配備版、台帳の書式・入力規則・対象行、DBの対象レコードを控える。Existing Script Propertiesとトリガーのキー・所有者・実行頻度も記録する。対象少数車両で書込み・同期とLINE表示を照合する。途中で不一致があれば新しい保存入口を止め、旧API/旧GASデプロイへ戻す。影響行を履歴と突合して台帳で個別復旧し、既存同期で複製を修正する。稼働中の他のトリガーや全件データは操作しない。
