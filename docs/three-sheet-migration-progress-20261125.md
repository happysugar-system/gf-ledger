# 車両管理3シート移行の進捗接続

共通保存のベースは 29761947b1431573d73b196bf3dbb0717fa31384。動的割当の側には月別納車、納車完了の候補があり、f48ef74 時点の変更を維持する。今回の進捗ワーカーは、既存の収録済み動的割当・受付照合を利用する。割当・取消の実地試験は利用者が合格済みで、繰り返していない。

## GAS台帳HTMLとの仕様照合

保存済みの GF_車両管理_HTML_返却日カレンダー修正(1).txt と GF_vehicle_server_full_mileage_20261110.gs を確認した。台帳HTMLでは GF_一覧取得、GF_詳細取得、GF_保存、GF_名変待ち一覧取得 を使用する。GF_保存 は列番号・元の表示値を受け、VehicleID、編集可否、数式、変更前の値、日付を検査する。今回の進捗保存はこの一般保存と分けて3項目に限定する。既存の返却予定、書類・写真・フォルダのリンク抽出と表示は接続時の退行確認に含める。

旧依存の移行対象は、30番系の車両同期と、それを呼ぶ登録・返却・予定・キューの経路。稼働コードで「車両状況」「利用者管理」を読む箇所と書く箇所を分類し、現行台帳の代替列と照合する。現時点では旧シートを操作していない。前使用者・前々使用者は既存HTMLの使用者欄に存在する。稼働中の貸出・返却・使用者変更の条件と更新順を照合し、取消や同一受付の再送で履歴が二重にずれないことを確認してから接続する。

## 検証用の進捗経路

- 検証Edge gf-assignment-dynamic-progress-test v1を goldfirst-demo に配備。read・save・status は既存スタッフACL、claim・replicate・finish は既存検証ワーカートークンを使う。APIは進捗保存時に複製の版を検査し、既存の動的操作競合ガードを利用する。別の Supabase プロジェクトは拒否する。
- GASワーカーは既存の検証ブックガード、動的4タブ読取、LINE受付照合を再利用する。受付・DriverID・VehicleIDを同一GASロック内で照合し、共通保存から管理区分・納車可能日・納車確定日だけを更新する。台帳再読取と進捗複製の照合が完了するまで完了扱いにしない。
- 既存DBの複製トリガーを、ロールバック付きの試験トランザクションで検証。初期段階からの変更、納車2日付、両段階の日時履歴を照合した。試験行は残っていない。割当・進捗の既存競合ガードもデータベースの定義を確認済み。
- 自動テスト10件。共通保存6件、動的受付の再照合2件、Edgeの認証・拒否2件。GASとEdgeと画面を通す実書き込み試験は未実施。書込フラグは今回設定していない。

## 既存GASへ一括反映する場合

使用する検証先は既存「GOLD FIRST 名変待ち連携検証」。動的割当統合版を追加済みの同じプロジェクトに、GF_LedgerProgress_SharedSaveCandidate.gs と GF_LedgerProgress_DynamicValidation.gs を追加する。前者の同名関数を持つ旧候補を既に入れている場合は定義を重ねず、その候補を置換する。実地試験までは書込フラグを有効にしない。既存の doPost やトリガーを変更しない。

画面接続後に検証Edgeの GF_DYNAMIC_PROGRESS_WRITE_ENABLED と検証GASの GF_DYNAMIC_PROGRESS_GAS_ENABLED を有効にする。既存の検証トークンを使用する。検証排他の準備が揃ってから新規の進捗依頼を送り、GF_動的進捗検証キューを1件処理 を実行する。期待結果は verified。失敗時は同じ受付に別依頼を重ねず、台帳の3項目、複製、処理キューを照合する。

## 移行判定

稼働GASの台帳HTML・一般保存・貸出返却保存・同期ワーカーの実ソースを取得し、両方の画面の名変待ち登録・割当・取消、直接編集同期、LINE本人表示、既存カレンダーと書類リンクを接続・確認する。本番移行は操作試験合格と承認後。既存GAS版とスタッフ画面配備、対象台帳行と複製、設定とトリガーの控えを残す。問題があれば新規フラグを停止し、旧版へ戻し、影響した行のみ台帳から復旧・再同期する。既存シートの削除は対象外。
