# 車両管理3シート移行の進捗接続

共通保存のベースは 29761947b1431573d73b196bf3dbb0717fa31384。動的割当の側には月別納車、納車完了の候補があり、f48ef74 時点の変更を維持する。今回の進捗ワーカーは、既存の収録済み動的割当・受付照合を利用する。割当・取消の実地試験は利用者が合格済みで、繰り返していない。

## GAS台帳HTMLとの仕様照合

保存済みの GF_車両管理_HTML_返却日カレンダー修正(1).txt と GF_vehicle_server_full_mileage_20261110.gs を確認した。台帳HTMLでは GF_一覧取得、GF_詳細取得、GF_保存、GF_名変待ち一覧取得 を使用する。GF_保存 は列番号・元の表示値を受け、VehicleID、編集可否、数式、変更前の値、日付を検査する。今回の進捗保存はこの一般保存と分けて3項目に限定する。既存の返却予定、書類・写真・フォルダのリンク抽出と表示は接続時の退行確認に含める。

旧依存の移行対象は、30番系の車両同期と、それを呼ぶ登録・返却・予定・キューの経路。稼働コードで「車両状況」「利用者管理」を読む箇所と書く箇所を分類し、現行台帳の代替列と照合する。現時点では旧シートを操作していない。前使用者・前々使用者は既存HTMLの使用者欄に存在する。稼働中の貸出・返却・使用者変更の条件と更新順を照合し、取消や同一受付の再送で履歴が二重にずれないことを確認してから接続する。

## 検証用の進捗経路

- 検証Edge gf-assignment-dynamic-progress-test v1を goldfirst-demo に配備。read・save・status は既存スタッフACL、claim・replicate・finish は既存検証ワーカートークンを使う。APIは進捗保存時に複製の版を検査し、既存の動的操作競合ガードを利用する。別の Supabase プロジェクトは拒否する。
- GASワーカーは既存の検証ブックガード、動的4タブ読取、LINE受付照合を再利用する。受付・DriverID・VehicleIDを同一GASロック内で照合し、共通保存から管理区分・納車可能日・納車確定日だけを更新する。台帳再読取と進捗複製の照合が完了するまで完了扱いにしない。
- 既存DBの複製トリガーを、ロールバック付きの試験トランザクションで検証。初期段階からの変更、納車2日付、両段階の日時履歴を照合した。試験行は残っていない。割当・進捗の既存競合ガードもデータベースの定義を確認済み。
- 自動テスト10件。共通保存6件、動的受付の再照合2件、Edgeの認証・拒否2件。GASとEdgeと画面を通す実書き込み試験は未実施。書込フラグは今回設定していない。

## 既存GASへ一括反映する場合

使用する検証先は既存「GOLD FIRST 名変待ち連携検証」。動的割当統合版を追加済みの同じプロジェクトに、GF_LedgerProgress_SharedSaveCandidate.gs と GF_LedgerProgress_DynamicValidation.gs を追加する。前者の同名関数を持つ旧候補を既に入れている場合は定義を重ねず、その候補を置換する。実地試験までは書込フラグを有効にしない。既存の doPost やトリガーを変更しない。

画面接続後に検証Edgeの GF_DYNAMIC_PROGRESS_WRITE_ENABLED と検証GASの GF_DYNAMIC_PROGRESS_GAS_ENABLED を有効にする。既存の検証トークンを使用する。検証排他の準備が揃ってから新規の進捗依頼を送り、GF_動的進捗検証キューを1件処理 を実行する。期待結果は verified。失敗時は同じ受付に別依頼を重ねず、台帳の3項目、複製、処理キューを照合する。

## 移行判定

稼働GASの台帳HTML・一般保存・貸出返却保存・同期ワーカーの実ソースを取得し、両方の画面の名変待ち登録・割当・取消、直接編集同期、LINE本人表示、既存カレンダーと書類リンクを接続・確認する。本番移行は操作試験合格と承認後。既存GAS版とスタッフ画面配備、対象台帳行と複製、設定とトリガーの控えを残す。問題があれば新規フラグを停止し、旧版へ戻し、影響した行のみ台帳から復旧・再同期する。既存シートの削除は対象外。

## 添付GASバックアップとの照合・切替前の取得対象

添付ZIPの12本のGSには現行台帳HTML、`GF_保存`、マニフェスト、配備版情報が含まれない。267efebの共通保存は割当済み車両の3項目だけを更新する。添付版の同期処理と置換関係にはなく、貸出・返却・予定・証憑処理を移植するには稼働版の呼出経路が必要。

| 添付ファイル | 照合が必要な経路 |
| --- | --- |
| 20_車両管理、30_車両同期、39_台帳ステータス同期 | 共通同期、台帳編集トリガー、旧2シートへの投影、前使用者の旧行参照 |
| 24_実績取消、25_車両実績、41_代車情報連動 | 貸出・返却の実績、代車と取消前後の復元、同期キュー |
| 40_車両予定カレンダー | 予定管理、CalendarEventID、台帳予定日編集、旧2シートの画面表示リンク |
| 80_スマホ画面 | 貸出表示の利用者管理参照、写真・書類のリンク反映 |
| 名変割当同期、190_返却受付_車両管理、191_返却_GitHub受信、194_返却受付移行 | 旧割当経路、返却受付・写真・LINE転送と実績確定の境界 |

本番台帳の「拡張機能 → Apps Script」で紐付くプロジェクトを開く。「デプロイ → デプロイを管理」で現行Webアプリの配備版を確認し、Headと異なる場合は「プロジェクトの履歴」で該当版とHeadを識別する。上表の現行ファイルに加え、`GF_保存`、`GF_詳細取得`、`GF_名変待ち一覧取得`、`doGet`・`doPost`の定義ファイル、`doGet`から読み込む現行HTMLとinclude先、`appsscript.json`を取得する。マニフェストは設定でエディタへの表示を有効にできる。トリガー画面から関数名・イベント種別・頻度を控える。共有前にキー・トークン・個人データを除外する。

検証ワーカーは、割当照合・共通保存の関数とSheets APIが欠けている場合、キューを取得する前に `validation_progress_dependencies_missing` で停止する。既存統合GASに共通保存と検証アダプターを追加または同名候補を差し替え、Sheets APIの既存有効化を確認する。検証用の設定のみを使い、台帳・複製・マイページを照合できるまでは本番切替を保留する。

## 11月26日 フォーム側エクスポートとの照合

添付JSON（10ファイル）にはフォーム側の `doGet`、`GF_車両管理_HTML`、`GF_詳細取得`、`GF_保存` がある。旧ZIPの本体側とはプロジェクトが異なる。フォームのファイル名には「テスト」とあるが、固定の接続先は共有済みの本番台帳IDと一致する。添付のマニフェストは `USER_DEPLOYING` / `ANYONE_ANONYMOUS`。このエクスポートの `doGet` と `GF_保存` にはスタッフ本人・権限の検査がない。実配備の公開範囲や上流の認証は未確認。この状態のフォームへスタッフAPIの代理権限やトークンを渡すと、既存ACLを経由せずに保存を要求できる構成になる。

- 通常保存は `google.script.run → GF_保存`。旧表示値・列・数式を検査後にフォーム側から台帳を書き込む。進捗APIへの呼出しはなく、納車可能日・納車確定日は日付処理と保存許可列に入っていない。現行の管理区分は既存のグループ一覧と保存検査に使われるため、進捗段階をそのまま流し込むとフィルタと保存検査に影響する。接続前に本体・台帳の見出しと既存グループ値を照合する。
- 既存HTMLは名変待ち割当を行番号・氏名、取消を行番号で呼ぶ。動的割当は受付・DriverID・VehicleIDと版照合を使う。切替では画面の形を維持し、裏側の引数と認証済みの送信経路を差し替える。受付の行番号や氏名から任意の対象を決めない。
- `GF_車両新規追加` の2定義は完全一致。 `scripts/gf-form-dedupe-export.mjs` は元JSONを保持したまま、その重複だけを除いたレビュー用出力を生成する。入力に対して変換し、HTMLとマニフェストを含む残り9ファイルの完全一致を確認した。ファイル単位で衝突する `無題 2` と `名変待ち割り当て` の7関数は処理が異なる。前者は別ブックの社長シート、後者は本体ブックの名変待ちと同期キューを使う。後者と旧ZIPの本体側ファイルも同一ではなく、本体側には追加の処理がある。定義を機械的に削除すると受付や同期の振る舞いが変わる。
- `前使用者` と `前々使用者` はフォームの既存欄に存在する。履歴を進める更新は、別の使用者が確定した保存と同じ書込単位にまとめ、取消時はその操作が記録した以前の値を照合して復元する。旧ZIPでは本体同期に「利用者管理」から変更前の値を取得する処理がある。別プロジェクト間で Script Lock は共有されないため、フォーム側と本体側で独立に履歴を更新しない。

### 検証と復旧の順序

1. フォームWebアプリの配備版とアクセス設定、既存ポータルがスタッフ権限をどこで保証するかを照合する。本体側は稼働版の同期キュー実装・台帳編集トリガー・貸出返却取消の定義を添付ZIPと比較する。設定値や個人情報の共有は不要。
2. 既存の検証ブックだけを指すことをサーバー側で確かめ、認証済みスタッフの操作を既存の保存APIへ接続する。台帳の書込元を統一し、Sheets API再読取とSupabase照合の後に保存完了を表示する。台帳直接編集からの同期は既存トリガーとの重複を確認する。
3. 未使用の検証データで、受付→割当→取消・再割当→進捗・納車日→マイページを結合確認する。使用者履歴、返却予定・CalendarEventID、写真・書類・Driveリンクは切替前後の値を比較する。
4. 現行の配備版番号、関係する台帳の対象行と既存トリガーを控える。切替は承認後。障害時は新規受付を止め、処理中のキューを照合し、旧配備版へ戻す。修復対象行は台帳と複製を比較して確定する。
