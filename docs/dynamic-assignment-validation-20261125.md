# 動的割当の検証配備と切替判定

## 実施済み

- 既存 goldfirst-demo に動的キューワーカー v2、動的スタッフ受付API v1を配備。未認証呼び出しは両方401。書込有効化フラグは今回設定していない。
- 既存キューのRLS、匿名の読み取り不可、ブラウザのINSERT不可、受付・ドライバー・車両に対する3つの一意制約を確認。別受付から同じ車両への同時有効依頼はDBで拒否されることをロールバック付きで確認。
- 既存検証台帳の空欄に V900004 を追加。TEST-V01行を再読取して変更がないことを確認。既存2冊から取得した実データの写しを純粋関数に渡し、TEST-R04 / D999904 / V900004 が割当可能と判定した。実際の割当は実行していない。
- 自動テスト19件合格。キュー取得・保持時刻・複製照合の3件を新規追加。

## 処理と状態

スタッフ受付APIは既存と同様にSupabase Authと gf_reception_access の owner/staff を使う。投入はサーバー生成の台帳バージョンが必要。同一IDの再送は既存結果を返し、別内容の同一IDは409。GASは取得したジョブの保持時刻と申込情報、台帳バージョンを再照合してから3シートをまとめて保存する。検証複製の書き込みは V9 で始まる検証車両に限定。反映を読み返してから verified にする。保存開始後の障害は reconciliation_required とし、通信断で処理結果不明のジョブを自動で取得し直さない。

既存UIへのボタン・版取得の接続は未完了。既存のスタッフ検証画面は名変待ち登録用。動的受付APIを配備した状態と画面から操作可能な状態を分けて扱う。進捗・納車日・マイページは既存固定ID経路が残っており、本検証の複製は初期割当・取消の値だけが対象。

## GAS操作

既存「GOLD FIRST 名変待ち連携検証」の編集URLで操作する。対象Script IDと2冊の設定をランタイムで照合する。

1. 既存コード・設定キー・トリガーを控える。既存の検証GASへ、integrations/gas/review/GF_ReceiptAssignmentReviewBundle.gs の内容を同名ファイルで追加する。同名ファイルがあれば差し替え。8つの個別モジュールが既に入っている場合は統合版との二重定義を避け、個別モジュールの差し替えだけを行う。
2. 高度なGoogle Sheetsサービスを既に使用できること、既存の検証2冊への権限、既存の GF_VEHICLE_DEMO_SYNC_TOKEN が同じ検証ワーカー用であることを確認する。既存設定は消さない。既存の doPost とトリガーは変更不要。
3. GF_動的割当検証_読取診断 を1回実行する。期待ログは connected:true、write_enabled:false、assignment_planned:true。キューや台帳に書き込まない。
4. 画面側のバージョン取得と操作入口が確認できた後に限り、検証Edgeの GF_DYNAMIC_ASSIGNMENT_STAFF_ENQUEUE_ENABLED と GF_DYNAMIC_ASSIGNMENT_CLAIMS_ENABLED_V2、検証GASの GF_DYNAMIC_ASSIGNMENT_GAS_ENABLED を有効化する。GF_動的割当検証キューを1件処理 は確保済み操作を1件処理し、結果を verified、reconciliation_required または rejected として返す。今回の作業では有効化しない。新しいトリガーは作らない。

## 本番移行と復旧

本番の認可済み入口、現在稼働中の定期同期、本人LINEマイページの接続を確定する。上記検証専用Edgeと固定検証IDを本番に持ち込まない。3シート保存、取消、古い画面、同時送信、納車日と進捗後の取消拒否、台帳直接編集、本人表示まで検証する。旧GAS版、スタッフAPI、入力規則を含む台帳、対象DB行を控え、承認後に少数車両で切り替える。障害時は新規受付と取得フラグを先に停止し、未完了を照合してから旧配備へ戻す。台帳の影響行のみを個別に復旧し、既存同期で反映する。既存データ・トリガーの一括置換を行わない。
